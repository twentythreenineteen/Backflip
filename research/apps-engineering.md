## Manifest, assets and structure

All four sampled manifests declare `FlipperAppType.EXTERNAL`, distinct `appid` and entry point, stack size, category and icon. GPS allocates 1 KiB for the app stack and uses a `fap_private_libs` entry for `minmea` with `timegm=mktime`; Unitemp and I2C Tools specify 4 KiB and `fap_icon_assets`. These are examples, not interchangeable values or proof of sufficient stack. GPS requires its submodule at checkout; its [build workflow](https://github.com/ezod/flipperzero-gps/blob/b70d7d8126a66f66a7a9cb34575ce5f71e399856/.github/workflows/build.yml) explicitly requests recursive submodules.

SigRoam's manifest separates the app-menu icon (`fap_icon="icons/sigroam.png"`) from compiled asset directory (`fap_icon_assets="assets"`). It explicitly excludes `tools/` from its source patterns to avoid compiling host-test `main.c` into the FAP; the manifest explains the recursive-glob concern. Confirm source inclusion and generated symbols against the **chosen SDK**, rather than copying project comments as universal rules. Unitemp has separate scenes, views, interfaces and sensor files; GPS keeps its UI and UART in two main C files. Complexity determines structure, not a mandatory directory template.

## Lifecycle, navigation and input

- Unitemp allocates GUI, dispatcher, scene manager and modules, registers each view, attaches the dispatcher fullscreen, routes custom/back/tick events to the scene manager and starts it. [App source](https://github.com/quen0n/unitemp-flipperzero/blob/ae6271000f9f4a06ea8f36bb86229159331d9e6e/unitemp.c). Its [menu scene](https://github.com/quen0n/unitemp-flipperzero/blob/ae6271000f9f4a06ea8f36bb86229159331d9e6e/scenes/unitemp_scene_menu.c) creates submenu items on enter, forwards selections as custom events, changes scene on event and resets the submenu on exit. SigRoam uses an X-macro scene list to produce matching enter/event/exit handler arrays in its [dispatch table](https://github.com/pingequalab/sigroam-wardriving/blob/df5d66f5e25cab7334137884b2c352a06efb58db/scenes/sigroam_scene.c); its [dashboard view](https://github.com/pingequalab/sigroam-wardriving/blob/df5d66f5e25cab7334137884b2c352a06efb58db/views/sr_view_dash.c) has custom input and view-model updates alongside stock GUI modules.
- GPS instead uses a `ViewPort`, draw/input callbacks and an eight-element message queue, with the application loop handling short and long input. Its [README](https://github.com/ezod/flipperzero-gps/blob/b70d7d8126a66f66a7a9cb34575ce5f71e399856/README.md) documents long Back to exit. A scene manager is therefore not inherent to every FAP.
- Cleanup has dependency ordering: SigRoam requests worker stop, stops RX, joins the worker, closes I/O, removes registered views, frees modules/dispatcher/scene manager, closes records and frees state ([source](https://github.com/pingequalab/sigroam-wardriving/blob/df5d66f5e25cab7334137884b2c352a06efb58db/sigroam.c)). Unitemp also removes views before freeing them and closes its records ([source](https://github.com/quen0n/unitemp-flipperzero/blob/ae6271000f9f4a06ea8f36bb86229159331d9e6e/unitemp.c)). Do not infer that all failure paths or thread shutdowns are safe merely because the normal path frees objects.
- Concurrency policies differ. SigRoam's custom and tick handlers use zero-wait mutex acquisition and can drop events/ticks under contention, while back navigation follows a different path ([app](https://github.com/pingequalab/sigroam-wardriving/blob/df5d66f5e25cab7334137884b2c352a06efb58db/sigroam.c)). Dropping input is an explicit tradeoff, not a general recommendation; evaluate which events must be delivered and which state is shared.

## Storage, peripherals and counterexamples

- SigRoam initializes defaults, loads a bounded settings file and reports statuses; for save it writes a temporary file, checks the full byte count and sync, closes, then attempts rename and removes the temporary file on failure ([storage implementation](https://github.com/pingequalab/sigroam-wardriving/blob/df5d66f5e25cab7334137884b2c352a06efb58db/src/sr_settings_store.c)). This reduces obvious partial-write risks; it is **not** proof of power-loss atomicity on every filesystem or firmware.
- Unitemp uses `APP_DATA_PATH` and `FlipperFormat` for settings. Its loader initializes defaults, but then ignores per-key read results and reuses `uint32_value`; a missing key can inherit the previous key's value instead of the comment's promised default ([source](https://github.com/quen0n/unitemp-flipperzero/blob/ae6271000f9f4a06ea8f36bb86229159331d9e6e/unitemp.c)). Example of why to check read results independently and validate loaded ranges.
- GPS's serial callback places received bytes into a stream buffer and signals its worker, which parses NMEA lines. Initialization acquires and initializes a serial handle; the worker deinitializes and releases it on shutdown, and the app signals and joins the worker ([UART source](https://github.com/ezod/flipperzero-gps/blob/b70d7d8126a66f66a7a9cb34575ce5f71e399856/gps_uart.c)). The UI also tracks previous OTG state and only disables power at normal exit if it enabled it ([UI source](https://github.com/ezod/flipperzero-gps/blob/b70d7d8126a66f66a7a9cb34575ce5f71e399856/gps.c)). The stream send return is not checked, so byte loss under pressure is not accounted for there. Its input callback uses `FuriWaitForever` on a bounded queue, potentially blocking when full. A mutex-allocation failure occurs after queue allocation and UART startup and returns after only `free(gps_uart)`, without the normal stop/join/release sequence. Treat as pitfalls, not templates.
- I2C Tools' [scanner](https://github.com/Tristus1er/flipperzero-i2c-tools-cli/blob/b53daecaa8eb0628e60e9f1f285dab8285dd41ec/i2cscanner.c) acquires the bus, tests addresses with a timeout, stores selected results as 7-bit addresses and releases the bus. Its choice of addressing and probe strategy is project-specific; check the current HAL contract and device safety before reuse.

## Firmware compatibility and verification

- Unitemp's [workflow](https://github.com/quen0n/unitemp-flipperzero/blob/ae6271000f9f4a06ea8f36bb86229159331d9e6e/.github/workflows/build_release.yml) builds with uFBT's official `release` channel. GPS's [workflow](https://github.com/ezod/flipperzero-gps/blob/b70d7d8126a66f66a7a9cb34575ce5f71e399856/.github/workflows/build.yml) uses a `dev`/`release` matrix and recursive submodules. Both use channel names, not immutable SDK versions.
- SigRoam's [FAP workflow](https://github.com/pingequalab/sigroam-wardriving/blob/df5d66f5e25cab7334137884b2c352a06efb58db/.github/workflows/fap-build.yml) builds separate Official, Momentum and Unleashed release-index rows, records SDK/API metadata and pins the action by commit. Its comments report differing API versions at a particular date; channels float, so do not treat those numbers as current guarantees. Its release commit message explicitly says the earlier v0.9 tag did not build on Official SDK. Build and link against every intended target, then test the produced FAP on matching firmware; a fork's symbols or private headers may not exist in another SDK.
- SigRoam's separate [host-test workflow](https://github.com/pingequalab/sigroam-wardriving/blob/df5d66f5e25cab7334137884b2c352a06efb58db/.github/workflows/host-test.yml) runs GCC and Clang against `tools/host_test`, including AddressSanitizer/UBSan; it explicitly disables leak detection. The [host tests](https://github.com/pingequalab/sigroam-wardriving/blob/df5d66f5e25cab7334137884b2c352a06efb58db/tools/host_test/test_line.c) exercise logic such as line parsing. Host tests are useful but cannot prove GUI, HAL, timing, allocation, actual SD failures or device behavior.

## Research verification and limitations

- Source links name exact commit SHAs and actual paths. Findings above derive from inspected contents, not search summaries; observations and hypotheses are labeled accordingly.
- Build, type check, lint, runtime tests, hardware tests and leak checks: **not run**; this is a source survey, not a code change. CI configuration is evidence of intended checks, not evidence of passing runs. No license compatibility analysis or exhaustive audit of either app is implied.
